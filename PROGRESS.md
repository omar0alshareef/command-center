- M1 versions: better-sqlite3 13.0.3 (prebuilt, loaded on Node 24 with no build tools), zod 4.6.5, tsx 4.23.15. FTS5 available (SQLite 3.53.4).
- M1 `schema_version` is created by the migration runner, not migration 002 (it must exist before any migration runs). Migrations are TS string modules, not `.sql` files, so they bundle without file-copy steps.
- M1 migration 002 also inserts built-in agents `operator` (human) and `system` (external) so `agent_log` FKs always resolve. `transition()` defaults `actor` to `operator`; other actors must be registered first (M4 auto-registers).
- M1 `transition()` triggers: start, complete, approve, reject, block, unblock, reset. Skip-step moves (todo→done, todo→review) from UI/UX §6.2 are not allowed by the core yet; add a confirmed `skip` path in M3 when the board needs it.
- M1 `start` throws `DependenciesIncompleteError` for unfinished `depends_on` unless `force: true` (board's "start anyway?").
- M1 `acceptance_criteria` is `{text, done}[]` and milestone `notes` is `{text, author, at}[]` (blueprint only says "JSON array").
- M1 `lessons_learned.fix_applied` is '' on reject; M10 fills it (and writes LESSONS_LEARNED.md).
- M1 write transactions use `BEGIN IMMEDIATE` (`write()` helper): deferred read→write upgrades fail with SQLITE_BUSY_SNAPSHOT, which busy_timeout does not retry.
- M1 activity feed pages by `(timestamp, id)` cursor, not offset, so live inserts don't shift pages.

- M2 IPC surface: `db:getAll`, `project:get|choose|retry`, events `db:changed`, `db:status`. Renderer only imports types from core (never runtime values: it would pull in the native module).

- M4 tools (D10, 25): read 9 (`get_task_context`, `get_task_summary`, `get_project_status`, `get_milestone_overview`, `list_tasks`, `get_task_history`, `list_agents`, `get_activity_feed`, `get_lessons_learned`), task 10 (`start/complete/approve/reject/reset/block/unblock_task`, `update_task`, `log_action`, `enrich_task`), milestone 5 (`add_milestone_note`, `set_milestone_dates`, `update_drift`, `create_milestone`, `add_milestone_task`), agent 1 (`register_agent`). - M4 identity (supervisor caution): the caller is the **session agent**, derived from the MCP `clientInfo.name` (slugged; `claude-code` for Claude Code) or `COMMAND_CENTER_AGENT_*` env, auto-registered on its first write. Tools take an optional `agent_id` only to act for another **registered, non-human** agent; `operator`, `system` and human agents are rejected on every write tool. A client whose name slugs to a reserved or human id gets `<id>-agent`. `register_agent` offers only orchestrator / sub-agent / external; a sub-agent with no parent becomes the caller's child.
- M4 strict input schemas: the SDK's default zod object silently drops unknown keys, so `update_task({status:'done'})` would "succeed" doing nothing. All tools now use `z.strictObject` and reject unknown keys with a message naming them.
- M4 size caps (char/4 estimator, ROADMAP risk register): `get_task_context` ≤ 8,000 tokens with a truncation notice that names the tool for more; `get_task_summary` ≤ 500 tokens, shrunk field-by-field so the JSON stays valid (never chopped mid-string).
- M4 errors: every thrown value becomes an `isError` result; messages name the next tool (`start_task`, `unblock_task`, `register_agent`, `list_tasks`, `force=true`, ...); no stack traces. Server entry refuses to start without `PROJECT_ROOT` or without an existing `command-center.db` (it never creates a board), and writes nothing to stdout except protocol messages.
