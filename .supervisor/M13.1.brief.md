## Goal
Roster is built from production stages. Each team agent has an executor type: `agent`, `external` or `human`, and an optional `tool`. The planner asks only decision questions, never about roles or skills.

## Decisions (simplest option, record in PROGRESS.md)
1. Keep internal names `CAPABILITIES`, `capabilities`, `capability`. Add media stages to the list: `script`, `edit`, `voiceover`, `thumbnail`, `publish`. The stage named in the planner is `plan_stages`; rename the `PLANNER_STAGES` entry and the prompt case, keep the output field names. Record the rename in PROGRESS.md.
2. Executor defaults live in code, one table `STAGE_EXECUTORS`:
   - frontend, backend, database, security, design, marketing, devops, qa, data, script: `agent`
   - edit: `external`, tool `Video editor`
   - voiceover: `external`, tool `Voice tool`
   - thumbnail: `external`, tool `Image tool`
   - publish: `human`
3. `TeamRole` gets `executor` (default `agent`) and `tool` (nullable). `proposeTeam` sets them from the role's capabilities: if any capability is `human`, role is `human`; else if any is `external`, role is `external` with the first tool; else `agent`. The operator can override both in the Team tab; the stored proposal is what gets approved.
4. Migration `006_executor.sql`-style TS module, same pattern as 005: `ALTER TABLE agents ADD COLUMN executor TEXT NOT NULL DEFAULT 'agent' CHECK(executor IN ('agent','external','human'))` and `ALTER TABLE agents ADD COLUMN tool TEXT`. Existing rows read back as `agent`. Built-in `operator` stays type `human`; executor for built-ins is `human` for operator and `external` for system (set in the migration with UPDATE).
5. Tasks from external or human roles: `PlanTaskSchema` gets optional `brief` (string | null, default null) and `checklist` (string[], default []). The `plan_tasks` prompt asks for them when the task's role executor is `external` or `human`. On approve, store the brief as the task `prompt` and the checklist as extra acceptance criteria. Do not add a new table.
6. `registerAgent` accepts `executor` and `tool`. Agent type (`sub-agent`, `external`, ...) stays as is; executor is the new field. Use the executor, never the type, for dispatch decisions in M14.
7. MCP: `list_agents` output already dumps agent rows; add executor and tool to the output. No new write tools.
8. UI: Planning Team tab gets an executor select (agent / external / human) and a tool text field per role. Agent Hub agent row shows an executor chip. Keep both within the existing tab and card styles; no new screens.

## Interview prompt
Replace the "team and skills" wording in the interview prompt with decision questions: deadlines, budget, whether anyone appears on camera or speaks in their own voice, content limits, target audience. Add a unit test that the prompt contains no "skill" or "team" question wording.

## Exit criteria (from ROADMAP M13.1)
- Roster from stages: a roadmap with a design stage in one milestone and none in another produces a roster where only the first milestone has a design stage.
- External stage: a video roadmap with a voiceover stage produces an agent with executor `external`, tool `Voice tool`, and the task has a brief and checklist. No runner call for it.
- Decision-only interview: a seeded session with a fake runner output asks no role or skill question.
- Migration 006 applies on a 005 database; existing agents read back as `agent`; the CHECK rejects an unknown executor.
- Approval with mixed executors writes executor and tool per agent in the same transaction. The M13 fault-injection test still rolls back everything.
- Tests: stage schema, stage-to-role mapping, executor defaults, migration 006, approval with mixed executors, interview prompt wording. `tsc --noEmit` strict, lint, Vitest all pass.
- Real command output in the handoff. Do not claim a live run you did not do.
